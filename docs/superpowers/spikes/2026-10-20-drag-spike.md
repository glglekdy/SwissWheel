# 스파이크 결과: 드래그 중 휠 창 띄우기

- 날짜: 2026-10-20
- 코드: `spike/dragwheel/` (버림 코드, `windows` 0.61, Rust 1.99.1)
- 환경: Windows 11 Pro 10.0.26300, 단일 모니터
- 실행: `dragwheel-spike.exe --inject` 한 번 (약 2분 40초, 휠 열기 27회, 드롭 10회)
- 테스트: 사용자가 직접 수행, 결과는 로그로 확인

## 결론

**설계(spec 4.2)대로 진행 가능.** 저수준 훅으로 Space를 감지하고, 커서 아래 레이어드 창이 OLE 드롭 타깃이 되는 방식이 탐색기와 바탕화면 드래그 모두에서 동작했다. 변경 사항은 아래 "설계 변경" 한 가지뿐이다.

### 참고: 바탕화면 mp4가 휴지통에 있음
테스트 뒤 `C:\Users\kimji\Desktop\2026-10-12 01-25-45.mp4`가 휴지통에 있었다. 휴지통 기록상 삭제 시각은 23:51:17 KST로, 로그상 약 956~957초에 해당한다. 휠 드롭(950.9초)보다 약 5초 늦고, 그 사이에 휠은 열리지 않았다. 드롭 결과로 원본이 지워지는 경우(소스가 MOVE를 처리하는 경우)라면 드롭이 끝나는 즉시 지워지므로 이 패턴과 맞지 않는다. 휠과 상관없는 사용자 동작(휴지통에 끌어다 놓기나 Delete 키)으로 판단했다. 사용자에게 확인했지만 답은 받지 못했다. 다음 단계 수동 체크리스트에 "드롭 후 5초 이상 원본 존재 확인"을 넣는다.

## 설계 변경 (spec에 반영)

1. **시간 초과 후 재열기 억제:** `TIMEOUT`으로 닫힌 뒤에는 `open_key`를 뗄 때까지 또는 왼쪽 버튼을 놓을 때까지 휠을 다시 열지 않는다. 그 사이의 `open_key` 키 반복은 삼키지 않고 그대로 통과시킨다. 파일 드래그가 아니었으므로 원래 앱이 Space를 받아야 한다.
2. **마우스 업 처리 확인:** 저수준 훅의 `WM_LBUTTONUP`은 OLE `Drop`보다 먼저 온다. 그래서 휠을 즉시 닫지 않고 200ms 기다린 뒤 닫는 방식을 그대로 쓴다. 이 방식으로 드롭이 누락된 적은 없었다.

## 다음 계획에 넘기는 사항
- 0픽셀 `SendInput` 주입 방식을 그대로 쓴다.
- 레이어드 창(`WS_EX_LAYERED|TOPMOST|TOOLWINDOW|NOACTIVATE`)과 `RegisterDragDrop` 조합은 그대로 쓴다. 본 구현에서는 GDI 대신 DirectComposition과 Direct2D로 그린다.
- `windows` 0.61 기준으로 필요한 기능 목록: `Win32_System_Com_StructuredStorage`가 있어야 `IDataObject::GetData`와 `ReleaseStgMedium`을 쓸 수 있다.
